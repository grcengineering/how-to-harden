Usage — appended to the implementation heading it makes a claim about, on the SAME line, and nowhere else: #### ClickOps Implementation{% include status-mark.html status="ai-validated" evidence="Console path observed live" date="2026-08-19" %} #### Code Implementation{% include status-mark.html status="ai-validated" evidence="API audit pack executed against a live tenant" date="2026-08-19" %} WHY THE MARK MOVED HERE (2026-08-20). It used to sit once at the top of the requirement, above `**Profile Level:**`, where it asserted "this control was validated" — averaging over two different acts and hiding which one happened. buildkite is the proof that was lossy: 3.1 was validated by applying Terraform to a live organization and was NEVER walked in the console, while 1.1 was console-only with no executed code. Both wore the same badge. Anchored to the heading, a mark makes exactly one claim about exactly one artifact. Params: status — ai-drafted | ni-drafted | ai-reviewed | ni-reviewed | ai-validated | ni-validated evidence — what was exercised for THIS surface. Required in practice: the mark asserts a specific act, and one without evidence is a mood. date — ISO date of the act. NO SPACE between the heading text and the include — also load-bearing, and it bites even though the mark itself renders no text. kramdown builds the anchor from the heading's raw text, so a trailing space becomes a trailing hyphen: `clickops-implementation-`, which then shifts every duplicate-numbered sibling to `--1`, `--2`, and so on. Measured on a real build, 2026-08-20. The gap you see beside the glyph is `margin-left` in the stylesheet, never a literal space. NO TEXT NODE — load-bearing, not a style choice.
