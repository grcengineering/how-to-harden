{% comment %} Per-requirement maturity badge. Usage — ONE line, immediately after the `### N.N Title` heading and BEFORE the `**Profile Level:**` line: ### 1.1 Enforce SSO with Domain Verification {% include status-badge.html status="ai-validated" evidence="Console path observed live" date="2026-08-19" %} **Profile Level:** L1 (Crawl) Two badges on one requirement (e.g. a control validated by both an agent and a person) go on consecutive lines in the same slot — they add, they do not replace: being both AI Validated and NI Validated is strictly more than either. Params: status — ai-drafted | ni-drafted | ai-reviewed | ni-reviewed | ai-validated | ni-validated evidence — what was actually exercised for THIS requirement. Required in practice: the badge asserts a specific act, and a badge without one is a mood. date — ISO date of the act. PLACEMENT IS LOAD-BEARING — every other slot breaks something silently: • inside the `###` heading → changes the kramdown anchor (2,300+ in-guide links and the packs' guide_url gate depend on those), corrupts the cheat-sheet control name, and breaks jumpToControl's prefix match. • same paragraph as, and before, `**Profile Level:**` → the cheat-sheet parser stops seeing the level, the control drops out, and if it is the only control the entire Cheat Sheet toggle disappears from the page. • under `#### Description` → the badge text is captured AS the description cell and the real description is lost. Between the heading and the Profile Level line it renders as its own block and the parser walks straight past it, leaving every parsed field byte-identical. What a badge asserts is exactly its agent and stage, no more: ai-validated → an AI agent exercised this requirement against a real tenant or console and the guidance survived. NOT a human review. ni-validated → a person applied and tested it on a real system. A requirement that was skipped, plan-gated, or only doc-checked gets NO badge.
