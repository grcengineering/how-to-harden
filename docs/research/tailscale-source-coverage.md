## Discovery boundary and method

The working inventory was opened before selecting new controls, using the official [feature index](https://tailscale.com/docs/features), [client index](https://tailscale.com/docs/features/client), separate [daemon reference](https://tailscale.com/docs/reference/tailscaled) and [system-policy reference](https://tailscale.com/docs/features/tailscale-system-policies). The feature index exposes state storage, client governance, sharing, routing, integrations and separate products; it is not just an index of tailnet-policy fields. Feature/configuration bodies, limitations, version/default history and recovery were then read. Existing headings and `last_updated` did not bound discovery.

All linked configuration sources below were read through the web retrieval tool on 2026-11-05; source-code/schema files were read through the authorized GitHub connector. Each row records a content-specific observation. An index is a discovery lead, not proof that every linked feature works. Earlier direct shell HTTP attempts did not complete; successful web/GitHub retrieval is a distinct fallback, not a relabeling of those failures. No signed-in Tailscale console was accessed. Search results that only mention Tailscale were not admitted as configuration authority.

Scope is core tailnet administration and its installed client/daemon, system-policy/MDM, posture, identity and workload-integration boundaries. Product protection of its own identity state is in scope even when the implementation uses TPM/Keychain. Generic disk/cloud/cluster hardening, secret rotation, separate PAM/Aperture administration and application deployment runbooks remain outside this guide.

## Conflicts, defaults and source limits retained

- **EncryptState Linux support:** the general system-policy page still has an older Windows/macOS-only sentence beside a Linux 1.102 support row. The Linux-specific loader reference and daemon reference establish the versioned alternatives; no backward support is inferred. The generator rejects older Linux JSON targets.
- **State posture type:** built-in attribute documentation lists Boolean values while an example quotes `true`. The collector preserves the response type. Missing/unrecognized values fail unknown. No state-based grant is shipped until the target policy engine is tested with true, false and missing values.
- **Approval versus SCIM:** retain the specific approval-reference prohibition and the conflicting generic recommendation; require a tenant/IdP pilot. This review does not settle vendor behavior by inference.
- **Recorder lifecycle:** specific SSH recording deprecation supersedes the general best-practice recommendation for new deployment advice. Existing fail-open/storage/recovery issues remain relevant until migration.
- **Routing defaults:** current CLI reference and [changelog](https://tailscale.com/changelog) describe version-dependent stateful-filter behavior, including an earlier default reversal. The guide requires review of the deployed version rather than extending one historical default to every client.
- **Security incident lead:** the vendor's [Hugging Face intrusion account](https://tailscale.com/blog/hugging-face-intrusion) prompted review of reusable enrollment keys and copied identity state. Configuration requirements originate from the feature/setup references above. This does not claim that one setting would have prevented the entire incident.
- **Search boundary:** the current official CIS/SCuBA searches did not identify a Tailscale-specific configuration baseline; NSA/ACSC searches likewise did not surface one. This is a search result, not universal absence. DISA's public index did not establish coverage. Searches of Datadog Security Labs, Wiz, Unit 42 and Trail of Bits did not produce a new product-specific configuration source; general mentions/SAML commentary were not converted into controls. The vendor references remain the configuration authority for this update.
